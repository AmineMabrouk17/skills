# Triage

Faites avancer les issues du project issue tracker dans une petite machine à états de rôles de triage.

Si ce repo traite les pull requests externes comme une surface de demande (voir la configuration de l'issue tracker), le triage les couvre aussi : **une PR est une issue avec du code attaché**, avec les mêmes rôles, les mêmes états et la même machine, avec quelques différences marquées « pour une PR » ci-dessous. Résolvez un `#42` nu vers une issue ou une PR selon la configuration du tracker.

Chaque commentaire ou issue publié dans l'issue tracker pendant le triage **doit** commencer par cet avertissement :

```
> *This was generated by AI during triage.*
```

## Documents de référence

- [AGENT-BRIEF.md](AGENT-BRIEF.md) : comment rédiger des agent briefs durables
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) : comment fonctionne la base de connaissances `.out-of-scope/`

## Rôles

Deux rôles de **catégorie** :

- `bug` : quelque chose est cassé
- `enhancement` : nouvelle fonctionnalité ou amélioration

Cinq rôles d'**état** :

- `needs-triage` : le mainteneur doit évaluer
- `needs-info` : en attente d'informations complémentaires du rapporteur
- `ready-for-agent` : entièrement spécifié, prêt pour un agent AFK
- `ready-for-human` : nécessite une implémentation humaine
- `wontfix` : ne sera pas traité

Pour une PR, les mêmes états se lisent par rapport au code attaché : `ready-for-agent` signifie qu'un brief est attaché et qu'un agent doit faire l'étape suivante sur le diff ; `ready-for-human` signifie qu'elle est prête à être mergée par un humain.

Chaque issue triée doit porter exactement un rôle de catégorie et un rôle d'état. Si des rôles d'état entrent en conflit, signalez-le et demandez au mainteneur avant de faire quoi que ce soit d'autre.

Ce sont les noms de rôles canoniques. Les chaînes de labels réelles utilisées dans l'issue tracker peuvent différer. La correspondance devrait vous avoir été fournie. Sinon, demandez à l'utilisateur d'exécuter `/setup-matt-pocock-skills`.

Transitions d'état : une issue sans label passe normalement d'abord à `needs-triage` ; de là, elle passe à `needs-info`, `ready-for-agent`, `ready-for-human` ou `wontfix`. `needs-info` revient à `needs-triage` une fois que le rapporteur a répondu. Le mainteneur peut passer outre à tout moment ; signalez les transitions qui semblent inhabituelles et demandez avant de continuer.

## Invocation

Le mainteneur invoque `/triage` et décrit ce qu'il veut en langage naturel. Interprétez la demande et agissez. Exemples :

- « Montre-moi tout ce qui nécessite mon attention »
- « Regardons #42 » (issue ou PR)
- « Passe #42 à ready-for-agent »
- « Qu'est-ce qui est prêt à être pris par les agents ? »

## Afficher ce qui nécessite attention

Interrogez l'issue tracker et présentez trois catégories, les plus anciennes d'abord :

1. **Sans label** : jamais triées.
2. **`needs-triage`** : évaluation en cours.
3. **`needs-info` avec activité du rapporteur depuis les dernières notes de triage** : à réévaluer.

Lorsque les PR sont dans le périmètre, incluez les PR externes dans ces catégories et étiquetez chaque ligne `[PR]` ou `[issue]`. La découverte ne fait remonter que les PR *externes* (la configuration du tracker définit qui compte comme externe), donc la PR en cours d'un collaborateur n'est pas du travail de triage. Ce filtre ne concerne que la découverte ; une PR explicitement nommée est toujours triée quel que soit son auteur.

Affichez les compteurs et un résumé d'une ligne par élément. Laissez le mainteneur choisir.

## Trier une issue ou une PR spécifique

1. **Rassembler le contexte.** Lisez l'issue ou la PR complète (corps, commentaires, labels, auteur, dates ; pour une PR, le diff aussi). Analysez les notes de triage antérieures pour ne pas reposer des questions résolues. Explorez la base de code en utilisant le glossaire de domaine du projet, en respectant les ADR de la zone. Effectuez deux vérifications contre la base de code : (a) **redondance** : cherchez une implémentation existante du comportement demandé par concept de domaine (pas seulement par les mots de la demande), et indiquez où vous avez cherché. Si vous en trouvez une, c'est un `wontfix` déjà implémenté (étape 5). (b) **rejet antérieur** : lisez `.out-of-scope/*.md` et signalez tout fichier qui ressemble à cette demande.

2. **Recommander.** Indiquez au mainteneur votre recommandation de catégorie et d'état avec le raisonnement, ainsi qu'un bref résumé de la base de code pertinent pour la demande (y compris si elle est déjà implémentée). Attendez les instructions.

3. **Vérifier l'affirmation.** Avant tout grilling, vérifiez que l'affirmation tient. Pour un bug, reproduisez-le à partir des étapes du rapporteur. Pour une PR, confirmez que le diff fait ce qu'il prétend : récupérez-la, exécutez les tests ou commandes pertinents. Rapportez ce qui s'est passé : confirmé (avec le chemin de code), échoué, ou détails insuffisants (un fort signal `needs-info`). Une vérification confirmée rend l'agent brief beaucoup plus solide.

4. **Griller (si nécessaire).** Si la demande a besoin d'être étoffée, appelez l'outil Skill deux fois, pour « grilling » et « domain-modeling », et grillez-la jusqu'à lui donner une forme, une série de questions à la fois, en affinant les termes de domaine et en mettant à jour `GLOSSARY.md`/les ADR au fil des décisions.

5. **Appliquer le résultat :**
   - `ready-for-agent` : publiez un commentaire d'agent brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human` : même structure qu'un agent brief, mais notez pourquoi cela ne peut pas être délégué (jugements, accès externe, décisions de conception, tests manuels).
   - `needs-info` : publiez des notes de triage (modèle ci-dessous).
   - Pour `wontfix`, fermez l'issue, avec un commentaire qui dépend de *pourquoi* :
     - **Déjà implémenté** : le changement existe déjà dans la base de code. Indiquez où il se trouve ; n'écrivez **pas** dans `.out-of-scope/` (cette base de connaissances est pour les demandes *rejetées*, pas pour celles qui sont construites).
     - **Rejeté (bug)** : donnez une explication polie, puis fermez.
     - **Rejeté (amélioration)** : écrivez dans `.out-of-scope/`, liez-y depuis un commentaire, puis fermez ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage` : appliquez le rôle. Commentaire facultatif s'il y a une progression partielle.

## Forcer rapidement un état

Si le mainteneur dit « passe #42 à ready-for-agent », faites-lui confiance et appliquez le rôle directement. Confirmez ce que vous êtes sur le point de faire (changements de rôle, commentaire, fermeture), puis agissez. Sautez le grilling. Si vous passez à `ready-for-agent` sans session de grilling, demandez s'il veut rédiger un agent brief.

## Modèle needs-info

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Consignez tout ce qui a été résolu pendant le grilling sous « established so far » afin que le travail ne soit pas perdu. Les questions doivent être spécifiques et exploitables, pas « merci de fournir plus d'informations ».

## Reprendre une session précédente

Si des notes de triage antérieures existent sur l'issue ou la PR, lisez-les, vérifiez si le rapporteur a répondu à des questions en suspens, et présentez une image actualisée avant de continuer. Ne reposez pas les questions résolues.
